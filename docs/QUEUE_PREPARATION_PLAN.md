# 队列修复与首页前置准备计划

更新：2026-09-19。工作分支：`feature/home`。

状态：计划已制定，尚未实施。依据：本轮对现有队列、会话协议、播放服务、界面及快照代码的只读检查。本文件不代表修复或测试已完成。

依赖关系：[核心交互规范](PLAYBACK_INTERACTIONS.md) → **本计划** → [首页功能计划](HOME_PLAN.md)。核心规范决定行为，本计划负责把现有代码迁移到该行为；首页不能继续依赖旧的 hash 去重队列。

## 目标与范围

在保留单个 MediaSessionService / ExoPlayer 的前提下，完成重复条目、四种播放操作、精确控制与旧记录兼容，为完整日推/歌单和 FM 提供可复用基础。

本阶段不接推荐接口、不开发首页内容或云端歌单、不请求真实账号反馈，不实现 FM 补歌，也不引入数据库、通用命令框架或第二套播放器。保留已有音频权限判断、试听裁剪、歌词数据层、账号隔离与请求取消机制。

## 步骤 1：条目标识、队列算法与快照迁移

这是一次连贯的数据模型迁移，不能只去掉去重判断。

- 增加轻量 `QueueEntry(entryId, song)`，Song 的 hash/专辑等仍用于业务请求；每次插入产生新的不透明唯一 ID，恢复时沿用保存的 ID，不因 Compose 重组重新生成。
- 队列保存 entries、currentEntryId 和按 entryId 排列的遍历顺序。选择、移除、上下首、随机及单曲循环均精确到条目。删除一条相同歌曲不影响另一条。
- 插入位置是当前项之后；没有当前项时为队首。随机模式同时更新实际遍历顺序，保证下一首确实是插入项；单曲循环仍只影响自然结束，不改变手动切歌的含义。
- 完整列表替换接受有序歌曲集合和选中索引，逐项生成 ID，保留重复、设为顺序播放。先验证非空和索引合法再原子替换；非法输入不清空当前队列。
- 快照升级到 v2。读取 v1 时为每个旧条目生成 ID，并把原 hash 当前项/遍历顺序映射到对应 ID，保留模式、进度、试听起点和会话归属。成功迁移后按正常原子保存流程写 v2；未知版本或损坏内容明确按既有恢复错误策略处理，不能编造可用队列。
- v2 校验 entryId 唯一、遍历完整、当前项存在，允许相同 hash 多次出现。只有活动队列，不增加进入 FM 前的旧队列备份。

完成标准：队列算法与记录读写能表达重复歌曲，迁移不丢失合法 v1 状态。临时兼容代码不得在最终交付中重新引入按 hash 选择条目的歧义。

## 步骤 2：服务命令、控制器与界面同步迁移

建议使用语义直接的操作命名，最终名称可随代码风格调整：

| 操作 | 输入 | 行为 |
| --- | --- | --- |
| insertAndPlay | Song | 新增下一项并立即播放，不查找旧 hash |
| enqueueNext | Song | 只新增下一项，当前播放/暂停状态不变；空队列选中新增项但暂停 |
| replaceAndPlay | 完整列表引用、选中索引 | 校验后整表替换并播放指定项，不用逐首命令模拟 |
| selectEntry | entryId | 切换既有项，不新增或重排 |

- 同步修改 PlaybackProtocol、PlaybackService、PlaybackViewModel、QueueSheet 和搜索回调，移除搜索对当前 hash 的插入禁用。队列移除也使用 entryId。
- 当前项状态及 MediaItem.mediaId 使用 entryId；歌曲 hash 仍通过 Song 提供给音频解析及歌词查询，不能把 entryId 当作酷狗歌曲 ID。
- 重试与进程恢复按当前条目重新解析，不调用 insertAndPlay。控制器重连后重新核对条目、会话及待执行意图；目标已消失则不执行，不通过“补插一首”伪装恢复。
- 拖动进度与歌词点击携带操作发起时的 entryId，服务端执行时再校验当前项，防止拖动期间切换到另一条相同歌曲后误定位。仅在 ViewModel 比较 Song 不足以保证这一点。
- PlaybackRequests 现有取消加请求版本校验继续复用；重复歌曲同 hash 也必须是不同播放请求。队列替换、切歌和账号变化使旧解析失效。
- 歌词内容可继续按 hash 复用；拖动状态、歌词跟随等与当前播放项有关的 UI 状态应按 entryId 重置，不强制重复下载相同歌词。
- 页面、系统通知和耳机上下首继续走服务的一套规则，不在 UI 维护第二份可独立修改的队列。

完成标准：搜索、下一首、队列点选/移除和重试形成端到端闭环，重复条目不会导致列表 key 冲突、多条高亮或误删；现有歌词和试听定位保持可用。

## 步骤 3：完整列表传输与异步替换边界

日推取消 30 首上限，后续云端歌单还可能分页，必须同时处理“整表导入”和“队列状态返回”的消息体积，不能只优化其中一边。

- 保持 UI 通过 MediaController 操作服务。建议采用应用私有的临时列表文件加不透明引用提交大列表：IO 写入完整元数据，命令只携带引用、选中索引和请求版本；服务只解析自己管理的引用，不接受任意路径或外部 URI。
- 传输数据仅为歌曲元数据，不含音频 URL 或凭据；临时记录按会话隔离，成功、取消、退出及启动清理孤立文件。复用小型文件工具，不搭建通用传输框架。
- 队列返回状态采用版本号与有界分批读取：会话 extras 只放当前项、数量、模式、队列版本等小状态，队列界面按需读取。读取中版本变化需丢弃旧批次，不混合不同队列；进度轮询不重复解码整表。
- 上述是优先方案；实施时若用更简单的有界分页协议，也必须满足原子提交、双向消息有界、会话隔离和取消清理，不能用“限制为前 30 首”回避问题。
- 私有文件和恢复快照的体积校验必须读写一致。以实际编码尺寸核对限制，超限明确报告，不静默截断、不保存一个无法恢复的成功记录。
- 为列表替换保留请求版本：取齐分页、读取完整元数据和校验完成前继续旧播放；失败不改队列。其间新的点播、选择、插入、清空或账号变化使旧的待替换操作失效，不能晚到覆盖用户的新选择。
- 原子替换完成后才解析选中歌曲的音频；此后如果无权限或解析失败，保留新队列并显示真实错误，不假装旧音频属于新歌曲。

完成标准：大列表不会通过单个巨大 Bundle 往返；整表按顺序到达，选中索引可靠，取消/失败不留下半份队列。分页业务接口由日推/音乐库阶段接入，本阶段只准备通用的完整列表入口。

## 步骤 4：为首页保留明确的状态边界

- 普通/FM 属于队列会话类型，与顺序/随机/单曲循环分开。基础阶段整理命令边界，FM 具体状态、推荐来源字段与补歌任务随 HOME_PLAN 接入，不伪造尚不存在的 FM 功能。
- 插入和点选操作不隐式改变会话类型；完整列表替换明确给出目标类型。日推/歌单替换到普通，FM 首批替换到 FM。
- 队列条目 ID 不能兼任 FM 推荐 ID。接 FM 时再根据真实响应增加必要的推荐来源数据，自动补歌去重与用户插入重复分开。
- FM 进入不保存旧队列、不提供恢复入口或 FM 清空功能；普通队列现有清空仍可保留。模式相关的按钮和服务端命令限制在 FM 阶段一起落实。
- 不为上述准备新建模块、通用策略工厂或复杂继承体系；优先围绕现有 Queue / Service 职责完成改动。

## 验证与提交安排

建议一个完整基础修复提交覆盖步骤 1–2 及必要兼容，另一个完整准备提交覆盖步骤 3–4；具体可随规模合并，但不能交付“内存允许重复、UI/快照仍要求唯一 hash”的中间状态。

优先修改现有测试，不为每个转发方法写测试。必要覆盖如下，允许一项测试包含同类边界：

1. 搜索重复点歌保留原条目、产生新 ID 并选中新项；下一首插入不改变当前项，当前歌曲也能再次插入；随机模式中插入确实位于实际下一项。
2. 按 entryId 选中/移除重复项只影响目标；整表替换含重复歌曲时仍选中指定位置，非法输入保留原队列。
3. 重试和控制器恢复不新增条目；同歌不同项切换后旧 seek/解析不能作用于新项。扩展既有请求取消测试，不依赖真实网络。
4. v1 迁移保留模式、顺序、进度和试听起点；v2 重复条目往返后当前项精确；账号不匹配记录继续拒绝。
5. 用一份有代表性的合成大列表检查有界传输、完整顺序、版本变化及失败不半替换，不做大量尺寸组合或压力基准。

完成代码改动后，在 `android/`、JDK 17 下执行：

```bash
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug
```

通过后进行一次针对性模拟器检查，不重复扩大测试：搜索同一首多次，队列中只高亮当前条目，点选/删除其中一条，暂停时插入下一首，重启后确认重复队列与进度恢复且不出声。再人工核对非零起点试听歌词跳转及通知栏上下首。完整列表入口在首页未接通前用测试验证，不往主应用添加演示歌单或临时调试入口。
