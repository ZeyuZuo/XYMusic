# 播放列表核心交互规范

确认日期：2026-09-19。适用于搜索、每日推荐、音乐库歌单、当前播放队列及 FM。

这是用户确认的目标规则，优先于旧播放阶段记录中的 hash 去重、已有歌曲直接切换等行为。步骤 1–2 已实现搜索/队列控制到 entryId；步骤 3–4 已实现有界传输与普通/FM 基础状态边界，人工闭环和真实 FM 业务尚未完成。

## 四种明确操作

这里的“来自歌单”指用户点击所在页面的上下文，不是查询这首歌是否属于某个收藏歌单，也不是检查它是否已在当前队列中。日推同样视为一个完整列表。

| 用户操作 | 队列变化 | 当前播放 | FM 状态 |
| --- | --- | --- | --- |
| 搜索等独立歌曲结果点歌 | 在当前项之后新增这一首的队列条目；保留原队列，即使有同一歌曲也不去重、不删除或搬走旧条目 | 立即切换并播放新增项 | 保持原状态 |
| 日推、我喜欢、自建/收藏歌单中点歌 | 按源列表原始顺序，用整个列表替换当前队列 | 播放用户点击的那个位置 | 退出 FM，进入普通列表 |
| 任意来源选择“下一首播放” | 只在当前项之后新增这一首；不导入来源列表、不去重 | 不切歌、不改变播放/暂停状态 | 保持原状态 |
| 当前播放队列中点一项 | 不插入、不替换、不重排 | 切换并播放点中的那一项 | 保持原状态 |

“全部播放”属于列表替换，从列表第一项开始。进入列表或刷新列表本身不改变播放。

没有当前项时，插入位置是队首；独立歌曲点播立即播放。“下一首播放”在空队列中仅加入并选中该项，保持暂停，不自动出声。随机模式的插入必须同时处于实际播放顺序的下一项，不能被随机遍历跳过；列表替换按源列表顺序启动顺序播放。

## 重复歌曲是合法队列条目

用户主动点播和“下一首播放”均允许重复，包括插入当前正在播放的同一首歌。队列内两条相同 hash 的歌曲是不同条目，选中和移除必须精确到用户操作的那一条。

例如，当前队列为 `[A, B, C]`，正在播放 A：

- 搜索点 C → `[A, C新, B, C原]`，立即播放 C新。
- 选择 B“下一首播放” → `[A, B新, B原, C]`，继续播放 A。
- 在当前队列点击 C → 队列仍为 `[A, B, C]`，播放原来的 C。
- 从日推 `[D, E, F]` 点击 E → 队列变为 `[D, E, F]`，播放 E；D 仍在 E 前面。

上例每条都从原始 `[A, B, C]` 开始。用户说的“移到当前歌曲之后”按“新增一条”实现，不移动原条目。列表替换也保留源列表的原始条目顺序，不擅自按 hash 合并重复歌曲。

## FM 是会自动补充的特殊列表

- 点击“猜你喜欢”启动 FM，以推荐列表替换当前队列并开始播放。不暂存旧普通队列，没有恢复普通队列入口。
- 已在 FM 时再点入口，回到现有播放页，不重新启动或替换；暂停时不会因返回页面自动出声。
- FM 中搜索点歌：插入下一项并立即播放，仍在 FM，播放完可继续推荐队列。
- FM 中任意来源的“下一首播放”：只插入单曲，继续 FM；当前队列点选也不退出 FM。
- 日推或普通歌单点歌/全部播放：完整列表替换队列并退出 FM，取消旧补歌任务；迟到响应不能重新混入。
- 返回首页、切换标签、搜索但尚未点歌均不退出 FM。没有“FM 清空队列”操作或自动恢复旧普通队列的行为。
- 自动补歌仍需有限去重，以避免服务连续返回同批歌曲；这是对新推荐批次的过滤，不能删除、合并或拒绝用户主动插入的重复条目。
- FM 推荐条目与用户插入条目保留来源区别，不能给插入的搜索歌曲编造推荐 songid 或自动套用推荐反馈。

普通的进程恢复仍存在：保存当前活动队列及模式，重启恢复为暂停。它与“退出 FM 恢复进入前的旧队列”是两件事，后者不做。

## 实现约束与实施顺序

具体修复范围、迁移步骤和验收见 [队列修复与首页前置准备计划](QUEUE_PREPARATION_PLAN.md)。本文件定义行为，准备计划定义现有代码如何迁移。

步骤 1–2 已把队列、命令和 UI 迁到 entryId；步骤 3 已实现私有文件传入完整列表、按版本分批返回队列和快照尺寸校验；步骤 4 已把普通/FM 会话类型与遍历模式分开，整表替换显式指定目标，插入/点选保持原类型。真实首页列表、业务分页及 FM 运行规则仍待接通。

1. 歌曲标识与队列条目标识分开：Song 继续保留 hash 等业务字段，队列项增加独立且可持久化的 entryId。选择、移除、当前项、随机遍历顺序及 UI 列表 key 都使用 entryId。
2. 服务提供明确的插入并播放、插入下一首、列表替换并播放指定位置、选中现有条目操作。不能靠“hash 已存在”推断用户意图；列表中的选中位置也不能只按 hash 寻找。
3. 快照升级并兼容旧记录，为旧条目生成标识，保留模式/顺序/进度；相同歌曲多个条目重启后仍能定位到原条目。迟到的解析结果按请求版本校验，不能因 hash 相同而误认为仍是同一请求。
4. 列表若有分页，替换前取齐完整列表，不能将当前已加载页冒充整个歌单。加载期间保留旧播放；失败保留旧队列并提示，取消或其他点播使旧替换请求失效。实现时控制跨进程命令体积，不将超大列表一次塞入 Binder Bundle。
5. 首批 FM 获取成功后才执行有效的替换；重复点击只保留一个启动请求。用户在等待时发起其他队列操作，应使旧启动请求失效，防止随后覆盖用户的新操作。

仅补关键测试：重复插入及原条目保留、下一首不切歌、完整列表替换并选中正确重复项、按 entryId 选择/移除及快照恢复。FM 接入时再验证插入保持 FM、列表替换退出 FM、迟到补歌失效。沿用既有构建验证，不扩大无关测试。
