# FM 阶段 3：显式反馈与待验收范围

2026-09-26。显式“不喜欢”已实现；真实反馈、设备交互仍待用户主动验收。自动播放时长与完成事件尚未接入，阶段 3 未全部完成。

## 协议依据与限制

上游基线、精确文件和核对结论见 [接口记录](HOME_API_CHECK.md)。文档明确 `action=garbage` 为“不喜欢”，hash/songid/playtime 是可选参数。当前发送推荐歌曲原始 hash、独立保存的 sourceId、实际待播数、platform=android 和布尔 is_overplay=false；不把 album_audio_id、队列 entryId 当成推荐 ID。

playtime 单位、试听/完整完成及正常播放事件触发语义未核实，因此省略可选时长、不发送自动播放反馈。没有根据名字猜测协议，也没有为核对协议修改真实账号偏好。真实 garbage 是否接受该最小请求及 songid 的关联仍需人工验收。

仅数字 status=1/error_code=0 被当作业务确认；HTTP 200、缺少字段或其他返回均不能显示成功。该成功条件沿用已观察的 FM 外层协议及上游错误封装，未宣称得到真实反馈样本验证。反馈可能附带新推荐，当前不消费它；独立补歌仍按现有有界去重规则串行进行，不因附带列表异常重复发送反馈。

## 实现边界

- Repository 使用独立的反馈请求类型，认证仍只在 API 客户端；POST 带 bypass 头，不把凭据或反馈放 URL。HTTP 客户端已禁用自动连接重试及重定向。
- FmCoordinator 共用单请求通道，补歌中暂不能提交反馈，提交中也不能重复提交或开始补歌；完成后检查在等待期间产生的补歌需要。两类状态分别发布，反馈错误不覆盖补歌错误。
- 服务校验账号和当前 entryId，仅 FM 推荐来源且有合法来源 ID 的条目可提交；搜索插入没有该入口。成功确认的条目在有界内存窗口中阻止重复提交，不建立持久反馈队列。
- 成功后只在当前项仍是原条目时切到后继，保持当时播放/暂停意图；无后继时暂停，保留条目并显示成功。失败不删除歌曲、不切歌、不停止有效音频，不自动重新提交。
- 失败结果可能是服务端已处理但响应未收到。再次点击原歌曲的“不喜欢”先显示重新提交说明，由用户确认；“重试获取推荐”只读推荐，不重发反馈。
- 下一首、试听结束、暂停恢复、强制停止后恢复均不发送 garbage。反馈不保存到磁盘，不补发旧操作；系统停止、普通列表替换和账号变化使旧结果失效。取消本地请求不能撤销已到达服务端的操作。
- UI 仅消费服务状态和发送命令，文案使用资源，按钮至少 48dp；没有第二套播放器、额外模块或通用反馈框架。

## 自动化与人工验收

新增必要测试使用合成数据和 MockWebServer，覆盖请求白名单、业务拒绝、来源校验、条目校验、串行与重复点击、失败后不自动重发、迟到响应及取消。真实账号不参与自动化测试。

JDK 17 下 `assembleDebug / testDebugUnitTest / lintDebug` 通过，100 项单元测试全部成功（新增 5 项），lint 为 0 错误、34 条警告。最终调试包已安装到开发模拟器，启动命令成功且进程存活；未自动进入 FM 或点击反馈，不能据此认定反馈交互、真实回执或设备场景已验收。

人工步骤（保持开发服务可用）：

1. 启动 FM，在推荐歌曲上看到“不喜欢这首推荐”；搜索点歌插入 FM 后不应有该操作，普通播放也不展示。
2. 仅对确实不喜欢的推荐主动点击：提交期间禁用；成功提示后切下一首。暂停时提交成功后下一首仍暂停。最后一首无后继时保持暂停。
3. 断网提交应提示未能确认，队列与播放不因反馈失败改变。恢复网络后不会自动补发；手动再次提交会说明可能重复，取消不发请求。
4. 普通下一首、锁屏下一首、试听结束、补歌重试不能产生“不喜欢”。恢复进程不自动播放或提交旧反馈。
5. 提交期间切歌，旧响应不得再切走新歌；提交期间点播日推、系统停止或退出账号，旧响应不得改变新状态。服务端可能已收到的操作无法撤销。
6. 补歌和反馈状态分别显示，深色、大字体和旋转后交互正常。继续按 FM 阶段 2 清单验收后台、耳机和恢复。

真实验证时只记录脱敏业务状态与字段结构，不保存完整响应、认证、真实歌曲标识或音频链接。自动播放反馈需后续获得时长单位、完成语义和可靠事件协议后再接入。
