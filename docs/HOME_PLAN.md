# 首页功能实施计划

更新：2026-09-19。分支：`feature/home`，基于已合并搜索、播放和歌词的 `main`（`44dee2f`）。

状态：队列前置步骤 1–2 已实现，人工验收未完成；步骤 3–4 与首页业务尚未开发。没有请求真实账号推荐、提交反馈或修改上游仓库。产品范围以 [V0.1.md](V0.1.md) 为准。

## 范围与交互

首页内容区只有“每日推荐”和“猜你喜欢”两张入口卡片，保留现有底部四栏和迷你播放器。不增加轮播、排行榜、最近播放等模块，不为装饰拉取额外数据。遵循 Material 3，封面只使用真实响应中的素材；没有封面时用现有通用占位图形。

- 未登录：卡片内说明需登录，点击进入现有登录页。返回后保留首页位置，登录成功不自动开始播放。
- 每日推荐：点击进入独立列表页；查看列表本身不改变当前播放。标题显示可确认的推荐日期和实际歌曲数，支持返回、加载、空结果、错误重试与刷新。
- 猜你喜欢：点击开始 FM，首批可用歌曲获取成功后再切换队列、播放并打开完整播放页。已有 FM 会话时仅返回播放页，不清空、不重复拉取；暂停状态保持暂停。
- 普通页面不展示接口地址、签名或平台参数。完整播放页复用现有封面、歌词、进度和试听处理，FM 只增加必要的模式说明和操作。

## 已确认的核心交互

统一遵循 [播放列表核心交互规范](PLAYBACK_INTERACTIONS.md)，不按歌曲 hash 是否已存在来决定点歌行为。

- 搜索点歌：新增到当前项之后并立即播放，允许重复，FM 中也不退出 FM。
- 日推或音乐库歌单点歌：整个源列表按顺序替换当前队列，播放点击位置；普通列表替换会退出 FM。
- 任意来源“下一首播放”：只插入这一首，不切歌、不导入整份列表、不改变普通/FM 状态，允许重复。
- 当前队列点选：切换到指定条目，不改变队列。
- 进入 FM 替换当前列表，不暂存旧队列、不提供恢复入口；FM 不提供清空队列功能。
- 日推有多少展示多少，没有 30 首上限；若有分页需取齐。列表刷新不改变当前播放。

喜欢、加入歌单随云端音乐库接入，本阶段不提供假按钮或独立本地喜欢列表。

## 前置阶段：队列修复与准备（首页开发基础）

必须先完成 [队列修复与首页前置准备计划](QUEUE_PREPARATION_PLAN.md)。该计划基于现有代码检查，覆盖：

1. 独立 entryId、重复条目与旧播放快照迁移。
2. 四种操作的服务命令、控制器及 UI 同步改造，重试/恢复不新增歌曲，定位精确到条目。
3. 完整列表的原子替换、有界传输及队列状态按版本读取，避免大列表和高频状态更新携带整表。
4. 普通/FM 状态边界与必要回归验证。

前置计划的完成条件全部满足后，再接本文件阶段 1 的日推业务；阶段 0 的接口文档核对可先进行。前置阶段不接 FM 网络、不做旧普通队列备份；步骤 1–2 实现完成不等于前置阶段已验收。

## 阶段 0：最小接口核对

先只读核对每日推荐和 FM 首批响应；真实账号的“不喜欢”和其他反馈仅由用户明确触发，不作为自动化测试步骤。保存脱敏字段结构或据此构造测试数据，不保存凭据、完整原始响应或临时音频链接。

已精确阅读上游 `module/everyday_recommend.js`、`module/personal_fm.js` 及对应文档，只能确认以下协议线索，不能视为业务已经联调：

| 接口 | 已知 | 实现前必须核对 |
| --- | --- | --- |
| `/everyday/recommend` | 上游转发 POST，platform 默认 ios，可传 android | 业务成功码、歌曲数组位置、顺序、总量、日期/时区、封面、hash 与专辑标识、空结果与认证失败 |
| `/personal/fm` | action 默认 play，garbage 表示不喜欢；支持 hash、songid、playtime、is_overplay、remain_songcnt；文档称剩余数大于 4 不返回推荐 | 首次请求与补歌参数、songid 对应字段、playtime 单位、事件和补歌是否合并、反馈成功码、空批次、试听结束语义 |

特别注意：

- 不把 `songid` 直接当成 `album_audio_id`，不沿用其他音乐平台 ID 逻辑。客户端时长统一毫秒，只有传输边界按已核实单位转换。
- platform 请求字段与账号 token 类型是不同概念；不为获得数据切换普通版/概念版 token。
- 日推展示接口提供的完整列表，不设 30 首上限、不从其他来源补齐，也不擅自去重源列表条目。未知或缺少关键字段的响应明确报错，不能静默丢弃后伪装空结果。
- 核查中转服务缓存是否影响 FM 补歌和账号隔离；不要在未核对前依靠重复请求或随意添加时间戳解决问题。
- 推荐源获取仍使用开发中转服务，保持 Repository 边界，方便后续 Kotlin 直连。没有真实样本前不预造业务 DTO。

## 阶段 1：每日推荐闭环

1. 增加 `data/recommendation/` 下的日推仓库与响应映射，复用既有 Song 和当前账号会话。
2. 增加 `ui/home/` 首页及日推列表状态，通过 ViewModel/StateFlow 消费；请求失败不影响正在播放的歌曲。
3. 日推列表支持单曲点播、下一首播放、全部播放。单曲点播和全部播放都使用播放服务的完整列表替换操作，分别选中点击位置和第一项；不通过循环发送搜索点播命令模拟。分页列表取齐后才替换，失败保留旧播放，传输方案避免超大 Binder 消息。
4. 替换队列时取消旧音频解析；新命令遵守现有会话版本校验。列表刷新、页面返回、切换标签不修改播放队列。
5. 加入小型缓存，不引入数据库。按服务地址、会话缓存归属与推荐日期隔离，只保存歌曲元数据、获取时间和日期来源；退出或切换会话清除，迟到请求不能写回旧数据。
6. 同一天再次进入复用缓存，提供显式刷新；跨天或缓存不适用时重新请求。优先服务端日期；若没有日期，记录本机获取日期作为缓存判断依据，并明确它不是服务端推荐日，不猜固定北京时间零点刷新。
7. 刷新失败保留旧列表并标记“上次获取的推荐”；过期缓存不冒充今天的结果。离线可以浏览缓存，点播仍需在线解析，不承诺离线播放。

完成标准：真实列表、真实数量、三种播放操作和账号隔离可用；重复进入不会改动队列；断网/空列表/跨天有明确状态。

## 阶段 2：FM 播放与有限续播

FM 的生命周期属于 PlaybackService，不能依靠首页是否可见或 Compose 重组触发补歌。保持单个播放器；用明确的普通/FM 会话类型区分，不让普通队列承担不清楚的隐含模式。

- 首次进入只发一个请求。连续点击复用正在进行的启动；首批失败或为空保留原播放和队列，显示可重试错误，不先清空用户内容。
- 剩余待播歌曲不包含当前歌曲；建议降至 2 首时补充，符合上游剩余数限制。一次只允许一个补歌任务，只对新推荐批次按 hash（忽略大小写）与同批、待播队列及最近播放窗口比对过滤；用户主动插入始终允许重复，不合并现有条目；窗口有上限，不长期保存全部听歌历史。
- 每次补歌若只返回重复项或空结果，不立即循环请求；保留当前和已有待播项，显示状态并允许手动重试。已有歌曲播完且无后继时停止，不能无限加载或无限跳歌。
- 后台、锁屏和页面“下一首”走同一条 FM 切歌逻辑。无权限、解析失败或网络错误不自动连续跳过多首。
- 退出 FM 时递增会话版本、取消补歌，迟到响应不能重新加入普通队列。系统停止也取消任务，迟到数据不能重新出声。
- 持久化原子保存当前活动模式、队列条目标识、当前项、有限待播队列和进度；重启只恢复为暂停，不拉推荐、不发反馈、不自动播放。用户点击继续后，重新解析音频并恢复有限补歌。
- 试听继续使用既有权限、裁剪和歌词时间轴。允许片段结束可以推进 FM，但不能据此声称完整歌曲已经听完。

完成标准：前后台可连续播放，重复点击不重复启动，补歌串行、有界，退出 FM 和进程恢复行为明确。

## 阶段 3：FM 反馈与收尾

反馈先核对协议再接通，不根据参数名字猜测业务语义。如果反馈与推荐请求耦合，统一串行处理，避免一次操作重复提交。

- 普通“下一首”不发送 garbage；只有用户明确点击“不喜欢”才提交该反馈。请求中禁用重复提交，检查业务结果；失败保留当前项、提示重试，不显示成功。失败后不自动重放可能已被服务端处理的反馈。
- 正常播放事件只在核实接口语义后接入。播放时长来自实际播放累计，不使用拖动后的进度冒充收听时长；暂停和缓冲不计入。试听结束与完整播放结束分别处理。
- 不在恢复进程时补发旧反馈，不做持久化离线反馈队列，不添加全量播放历史上报。
- 反馈失败与补歌失败分别提示，不能阻塞当前有效音频或偷偷标记“不喜欢”。若真实字段或语义仍不明确，明确报告未接通范围，不把 FM 阶段写成全部完成。

## 实现边界

建议文件放置：`ui/home/` 管首页与日推列表；`data/recommendation/` 管协议、映射和日推缓存；`playback/` 内只增加确有职责的 FM 状态/补歌协调代码。先复用现有会话与歌曲模型，不建通用推荐引擎、第二套播放器或万能管理类。

认证只进入 API 客户端，不能转发到封面/音频 CDN；播放地址仍在真正播放时解析，不保存到推荐缓存。推荐业务和播放状态分别管理，所有 UI 事件经 ViewModel/MediaController 进入服务。若复制上游代码才更新 THIRD_PARTY.md，本轮未复制实现。

## 验证与交付

每阶段单独提交并更新 README 的真实完成状态。只对新增行为补必要测试，不铺大量 UI 自动化，不用真实账号做自动化写操作。

- 日推：响应映射/失败与空结果区分、缓存归属与日期失效、全部播放替换队列（尽量扩展现有队列测试）。
- FM：用假的仓库验证并发补歌、重复/空批次停止、退出后的迟到结果、恢复不自动出声、搜索插入保持 FM、日推/歌单替换退出 FM、退出账号清理；协议明确后验证下一首和不喜欢的事件区别。时间单位只在必要边界断言。
- 每个可交付阶段运行 JDK 17 下 `assembleDebug / testDebugUnitTest / lintDebug`，通过后只做一次针对性模拟器检查。

人工重点验收：日推不足及超过 30 首均完整展示、点击中间歌曲整表入队、重复搜索点播新增条目、重复进入/刷新不打断播放、跨天与断网缓存、FM 连续播放与重复点击、锁屏下一首、从日推/歌单点播切回普通列表、试听结束、退出账号、强制停止重开、深色及大字体。真实反馈由用户在 App 中主动操作并确认。

## 当前结论与下一步

先完成 [队列修复与准备计划](QUEUE_PREPARATION_PLAN.md) 的验收，再核对日推字段并实施日推；日推交付后进入 FM。进入 FM 不保存旧队列，搜索插入保持 FM，日推/歌单替换才退出；反馈单位及完成语义由接口核对决定。
